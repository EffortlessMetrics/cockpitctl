# PR Comment ABI

This document specifies the stable structure of the PR comment generated by cockpitctl. Consumers (CI bots, dashboard scrapers) may rely on these markers and section order.

## Stable Markers

The cockpit comment is delimited by HTML comments:

```
<!-- cockpit:begin -->
...comment body...
<!-- cockpit:end -->
```

These markers are frozen. Tooling may use them to locate, replace, or extract the cockpit comment within a larger PR body.

## Section Order

Sections appear in the following fixed order within the markers:

1. **Header** — `## Cockpit` heading and attribution line
2. **Summary table** — per-sensor status table
3. **Highlights** — top findings across all sensors
4. **Annotations** — file-level findings with capping
5. **Sections** — sensor groups ordered by `section_order` from policy

## Summary Table

```
### Summary

| Sensor | Status | Blocking | Notes |
|---|---:|---:|---|
```

Each row contains:
- `Sensor` — sensor ID in backtick-code format (`` `sensor_id` ``)
- `Status` — verdict badge: `pass`, `warn`, `fail`, or `skip` with emoji prefix
- `Blocking` — `yes` or `no`
- `Notes` — report path in backtick-code, optional comment path, optional `_truncated_` marker

Status badges (frozen):

| Status | Badge |
|--------|-------|
| `pass` | `pass` |
| `warn` | `warn` |
| `fail` | `fail` |
| `skip` | `skip` |

## Highlights

```
### Highlights

(showing up to **N**)
```

Highlights are rendered as a numbered list:

```
1. BADGE **sensor_id**: `code` at `path:line` — message
```

- `BADGE` — severity emoji (`error`, `warn`, `info`)
- Location is omitted if no path is present
- Newlines in messages are replaced with spaces
- Empty highlights render as `_No highlights._`
- The cap value `N` is `max_highlights` from policy

Highlight ordering follows the [determinism contract](determinism.md#highlight-sort-key).

## Annotations

```
### Annotations
```

Annotations use the same format as highlights (numbered list with severity badge, sensor_id, code, location, message).

- Annotations are capped at `max_annotations` from policy
- Ordering: severity desc, blocking-first, sensor_id, path, line, code, message
- When truncated, an inline note is appended:
  ```
  _Showing M of N annotations (capped by `max_annotations`)._
  ```
- Empty annotations render as `_No annotations._`

## Sections

Sensor groups appear under `### Section Name` headings, ordered by `policy.section_order`. Sections with no sensors are omitted.

Each sensor within a section is rendered as:

```
- `sensor_id`: STATUS_BADGE · report `path` · comment `path`
  - repro: `command`
```

- Comment path is omitted if absent
- Repro line is omitted if not configured in policy

## Truncation Contract

Truncation is noted inline at the point where it occurs:
- Highlights: the cap is displayed in the `(showing up to **N**)` preamble
- Annotations: a `_Showing M of N annotations (capped by ...)._` line is appended when the limit is hit
- Summary table: the `_truncated_` marker appears in the Notes column for sensors whose findings were capped

No silent truncation. If output is reduced, the comment indicates it.

## Determinism Guarantee

Identical inputs (same `cockpit.report.v1` data and same `cockpit.toml` policy) produce byte-identical comment output. This enables diffing comments across runs to detect regressions.
